# 設定画面・修正後の独立実操作計画

評価対象は親から通知された固定ビルドのみ。各ケースは Playwright の新規 browser context と空の localStorage から開始し、必要な場合だけ [`after-fixtures.mjs`](./after-fixtures.mjs) の架空データを投入する。通常ユーザーデータには触れない。390×844 と 1280×800 は同じ空初期 state で比較する。製品コードから操作方法を補わず、表示されたリンク・ボタンだけで進める。

| ケース | 初期データと画面操作 | 画面上で確認する結果 |
| --- | --- | --- |
| 空・スマホ/PC | `empty`。初期画面から設定入口を探して開き、必須3項目の各リンクを1回ずつ試す。 | 入口までのスクロール・タップ数、最初の画面の占有面積、必須/補足の識別、戻りやすさ、横溢れとフッター遮蔽。各リンクは該当入力に到達する。 |
| 必須が一部だけ | `partial`（試験だけ登録）。設定を開く。 | 試験を再登録させず、教材・学習枠の未設定だけが分かる。試験の保存内容は残る。 |
| 必須完了・補足未確認 | `ready-unconfirmed`（試験/教材/学習枠あり、食事/授業/定期予定/例外未確認）。設定を開き、計画作成へ進む。 | 必須不足の表示は消える。補足の未確認と実際の登録/回答を区別できる。補足が未確認でも登録済みの条件から計画を作れる。警告を読むことが主操作の妨げにならない。 |
| 「予定なし」を明示 | `schedule-none`（授業/定期予定/例外を明示的に「なし」）。設定を開き、食事の状態も確認する。 | 3種の「未確認」が消え、空欄と「なし」が混同されない。食事未設定は別に残る。再読込でも同じ。 |
| 通知を非表示 | `ready-unconfirmed`。画面の「無視する」を1件押し、通知管理から再表示し、再読込する。 | 非表示はその通知だけに効く。必須不足や実データは変わらない。非表示/再表示状態が保存され、操作名から結果が推測できる。 |
| 値が不正 | `invalid-block`（3種は登録済みだが block=0）。計画作成を試す。 | 未登録の案内と値検証の失敗を混同しない。無効な設定の場所と直し方が分かり、保存済み設定や記録は勝手に書き換わらない。 |
| 必須登録の削除 | `schedule-none` から試験・教材・学習枠を別 context で1種類ずつ画面で削除。設定へ戻って再読込。 | 削除された種類だけ未設定に戻る。関連する他のデータがどう変わるか画面で分かる。再読込後も同じ。不可逆操作は誤操作防止が適切。 |
| 保存失敗 | 新規 context でデモの `Storage.setItem` を対象キーに限り失敗させ、画面で1件変更。 | 計画入力エラーと異なる保存障害が分かる。未保存の操作を保存済みに見せない。復旧後の状態を確認できる。デモ故障注入であり、native SQLite の障害確認とは区別する。 |
| 読み込み失敗 | 新規 context で対象キーの読み込み例外、別 context で不正 envelope を投入して起動。 | 空初期 state と誤認させず、読み込み失敗と復旧方法を示す。通常データを消さない。native SQLite の読み込み障害確認とは区別する。 |

変更前の画面と測定値は [`review.md`](./review.md) を基準にする。修正後はスクリーンショット、操作数、対象画面、期待/実際、目的への影響を記録する。ドメインの `validateSettings` による計画値の不正と、永続化層の保存/読み込み失敗は別のケースとして判定する。
