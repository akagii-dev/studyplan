# 日常フロー再設計の検証

## 目的と判定基準

対象は「今日の予定を見る → 同じ場所で実績を記録 → 翌日以降を自動調整」。問題集・周回ごとの予定と実績を分離し、通常の記録で画面遷移と再計算の承認を要求しない。設定変更や固定予定の競合がある場合は、実績を保持して解決先を示す。

評価中はビルドを固定し、ブラウザーの独立したコンテキストに架空データを置く。既存のデスクトップ保存データは使わない。

## 計算の独立した期待値

1問2分・総量20問・今日の予定10問、翌日は60分使用可、期限は翌々日（期限当日は配分しない）を基準にする。余裕率0、復習日0、他の教材・用事なし。

| 今日の実績 | 残量 | 翌日の配分 | 今日の予定 |
| --- | ---: | ---: | ---: |
| 未入力 | 20問 | 記録操作をしていない | 10問のまま |
| 明示的な0 | 20問 | 20問・40分 | 10問のまま |
| 5問 | 15問 | 15問・30分 | 10問のまま |
| 10問 | 10問 | 10問・20分 | 10問のまま |
| 15問 | 5問 | 5問・10分 | 10問のまま |

5問を8問へ訂正すると残り12問・24分。取消すると未入力へ戻り、残り20問・40分。今日の予定、過去予定、取消済みを含む記録履歴を再配分の都合で書き換えない。同一条件で再実行した配分と残量が同じであることも確認する。

翌日の枠を20分にした場合、実績5問なら10問を配置し5問・10分を未配置とする。実績15問で翌日に10問の固定予定がある場合、固定予定を5問へ無断で縮めず、実績15問を保存し、競合を示す。異なる教材・周回の問題数を「全体の達成率」へ混ぜない。

## 環境

- Windows、React / TypeScript / Vite、既存CSSのトークンを利用。
- ブラウザー版の保存は独立したlocalStorage。デスクトップ版はTauri / SQLite。
- 調査開始時はRust環境がなかったが、作業中のユーザーによる導入後にcargo / rustc 1.98.1、stable-x86_64-pc-windows-msvcを確認。Tauri / SQLiteの実機検証も実施対象に追加した。
- CUAは利用可能なブラウザーを返さないため、実ブラウザーの操作はPlaywright / Edgeで行う。

## 構造案の比較（variant）

「今日の問題集ごとの実績入力」を対象に、Structure軸で3案を独立HTMLへ実装し、実ブラウザーで切り替えた。1440 / 375 / 320pxで横はみ出しなし、0問入力、一括送信、次項目への移動、ピッカーのキーボード操作を確認した。

| 案 | 構造 | 適する利用 | 操作上のコスト |
| --- | --- | --- | --- |
| 行ごと | 予定・実績・入力を問題集の行に置く | 学習した一冊をその都度記録 | 複数冊を同時入力する場合は冊数分の送信 |
| 一括 | 全教材の入力を一つの送信へまとめる | 一日の最後に全件を記録 | 空欄と0、送信対象の確認が必要 |
| 順番 | 一教材を表示して記録後に次へ進む | 一度に一項目へ集中 | 他の教材を見るための前後移動 |

親エージェントが「行ごと」を採用。ユーザーは選択を委任しているため、スキルの通常の選択待ちは行わない。製品では入れ子のカードをやめて短い一覧にし、時間の目安と翌日の重複表示を二次画面へ移す。主ナビゲーションは今日・今後の予定・記録履歴・設定とする。

採用後の製品画面も、固定したビルドで実操作と独立評価を行う。

## 変更前の独立実操作

固定したデモビルドの主JS SHA-256は `236E2753B33E2C931D88155C7758C6BD9AD3F96A09E2BD52CA9E4CCB9EBF0738`。UX担当がPlaywrightの独立コンテキストで、今日10問・翌日10問・未入力から操作した。

- 今日の予定は起動後0操作で見えるが、主ナビゲーションには15項目（デスクトップ版では16項目）が並ぶ。
- 行の「記録」→別画面の「5問」→「記録する」まで3操作・1画面遷移。
- この時点では翌日10問のままで、不足分5問が反映されない。
- 「計画全体を見直す」→「この内容で更新」で追加2操作・1遷移。翌日15問となる。
- 配置の確認は「学習カレンダー」でさらに1操作・1遷移。
- 読む必要がある情報は対象日・教材・周回・追加問題数の選択、前倒し反映の結果、計画案と承認。調整が必要かの判断もユーザーへ残されていた。
- 320px幅の記録画面は文書幅430pxとなり、主要操作が横にはみ出した。Axeの違反数0でも、実操作上のHIGH所見として扱う。

変更前の計算テスト `pnpm test` は25ファイル・256件成功。

## 変更後の主フロー（第1回）

固定したデモビルド `index-CeDhP_zh.js` のSHA-256は `245688E87193DC3E95B45D07E2E30F3B507C88F791BBE7444C491E8A3E3C18D0`。親エージェントの実操作は `node scripts/daily-flow-smoke.mjs`、結果は `test-results/daily-flow/results.json`。

| 操作 | 変更前 | 変更後 |
| --- | --- | --- |
| 今日の予定を確認 | 起動後0操作 | 起動後0操作、問題集・周回別の一覧 |
| 5問の実績を入力・保存 | 3操作・1遷移 | 数値入力と記録の2操作・遷移なし（Enterでも送信可） |
| 翌日へ不足分を再配分 | 追加2操作・1遷移、案を承認 | 追加操作なし、保存と同時に15問へ調整 |
| 翌日の問題集別の量を確認 | 合計7操作・3遷移 | 合計3操作・1遷移 |

入力のたびの日付・教材・周回の再選択、再計画の要否判断、案の読解と承認が通常利用からなくなった。今日の予定と実績は同じ行へ集約し、時間の内訳、設定、詳細カレンダーは二次画面へ分けた。

### 親エージェントの実操作と計算照合

隔離したEdgeコンテキストで全12シナリオが連続成功。期待値は上記の小例から求め、保存内容と画面の双方を照合した。

- 0 / 5 / 10 / 15 / 20問を記録し、翌日は20 / 15 / 10 / 5 / 0問。未入力と0問を区別。
- 5問を8問へ訂正すると12問、取消すると20問。取消履歴を保持。
- 別教材「英語読解」全4問のうち予定外に2問を記録し、残り2問を配置。「民法過去問」の20問とは独立。
- 翌日20分の枠では10問を配置し、5問・10分を未配置として理由を表示。
- 固定10問に対して実績15問なら実績と固定予定を保持して確認を求め、5問へ訂正すると固定10問を守って残りを再配分。
- 最終学習日の実績5問なら残り15問・30分を未配置とし、今日の予定は保持。
- 確認待ちの設定案は上書きせず、実績を保存。
- 320px幅でも横はみ出しなく、Enterで記録して翌日の結果へ到達。
- 各記録後の再読み込みで実績・設定・予定を保持し、再配分の重複なし。ブラウザー実行エラーなし。

## デスクトップ版と回帰テストの更新

Rust導入後は、テスト専用のSQLiteとWebView2プロファイルをシナリオごとに作り、実際のTauriウィンドウで操作した。通常のユーザーデータは使用していない。

既存E2Eの画面操作は新しいナビゲーションへ更新した。削除した主画面のドーナツグラフへの検査は、教材・周回別の初期完了数、今日の実績、残量、訂正・取消、0問と未入力の検査へ置き換えた。計算期待値は出力に合わせて作り直さず、総量137問−初期完了23問−実績30 / 20 / 25 / 0問から、翌日以降84 / 94 / 89 / 114問と独立に定義した。

## 検証の限界

- 独立UX評価はEdgeのデモ版。Tauri / SQLiteの実操作と計算照合は親担当が別途実施した。
- スクリーンリーダー、RTL、アプリ全体の200%ブラウザーズーム、全経路のキーボード操作は未検証。時間内訳の200%文字拡大・文字間隔、全テーマとライト/ダーク、今日の320px入力は確認した。
- 容量不足・期限不足の理由は実ブラウザーで確認。その他の理由分岐は単体テストで検証した。
- リリース用実行ファイルはビルド済み。通常のユーザーデータを開かないため、配布用リリース実行ファイルそのものの起動は実施していない。ネイティブ実操作には同じ製品ソースのデバッグ版を使用した。
- 変更前のスクリーンショットは初回の旧E2E出力先の初期化で失われた。変更前の操作測定は監査文書に残り、変更後の証拠は `docs/ux-after-eval/` に保持した。E2E出力先も分離した。
